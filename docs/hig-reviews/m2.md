## Findings

1. **[PASS] Search bar and toggle** (`ui/content.rs`). Search: "The standard pattern for search in GNOME utilizes a search bar which slides down from beneath the header bar." and "The search button in the header bar, which should toggle."
2. **[FIXED] Type to search.** Search lists three ways to open search: "Typing, even when the search field is not focused", "Ctrl+F" and the toggle. The first was missing; typing now opens the bar in every view with search. Ctrl+F was already there.
3. **[PASS] Main menu above the sidebar, five items in two groups** (`ui/sidebar.rs`). Menus: "If the window has a sidebar, the primary menu should be placed above the sidebar list."; "Menus should contain between three and twelve items"; standard items "should be placed in a group at the end of the menu". Import and Export end in an ellipsis because they open file dialogs (writing style: "Use an ellipsis (…) at the end of a label if further input or confirmation is required").
4. **[PASS] Unavailable actions are insensitive** (Refresh, Import, Export, Preferences). Buttons: "Make invalid buttons insensitive, rather than showing an error message when the user clicks them." The menus page says nothing about hiding or disabling items.
5. **[PASS] One suggested pill button** (Add Podcast on the Shows empty state). Buttons: "Each view should only ever include a single button using either the suggested or destructive styles." and pill "can be used when a text button is situated in open space, and is a primary action for the view."
6. **[PASS] Empty states give guidance and an action.** Placeholders: "It is often helpful to include a description which provides additional guidance, such as how to add items." and "include controls for relevant actions, such as adding content". This closes the item deferred from M0.
7. **[PASS] Back at the start of the content header, only on deeper pages.** Header bars: buttons such as "_back_ … are placed at the start of the header bar". Changed after review (2026-10-29) from history to the page hierarchy; Add opened from the Shows button now has no Back.
8. **[PASS] Add above the sidebar list, at the start.** Sidebars: "Header bar controls which affect the sidebar list should be placed above the list." Header bars: "Buttons for the main user actions, such as _new_, _add_, _open_ and _back_. These are placed at the start of the header bar". Add moved here from the bottom of the sidebar after review (2026-10-29). Refresh then moved from the header into the main menu at the user's request, and a Refresh button was added at the start of the Shows and New headers (checked at 1440×900 light in Shows, New and Queue, and 360×640 dark in New); the menu has six items in two groups, within "Menus should contain between three and twelve items".
9. **[NOTE] Narrow sidebar style.** At 360px the sidebar uses `AdwSidebar`'s page mode (boxed rows with arrows, as in Settings) rather than the mockup's plain rows. The sidebars page does not describe the collapsed look; page mode is libadwaita's own pattern for a sidebar collapsed into a page.

## Deeper pages slide in (2026-10-29)

The content pane is now an `AdwNavigationView`; Add slides in over the current section. Checked headless with `build-aux/headless/shot.sh` and a log of `App`'s messages: + opens Add with the view's own Back; Alt+Left (focus in the sidebar), the header Back and repeated open/back cycles all return to the section underneath; after the simplification, + from Queue opened Add over Queue, Alt+Left returned to Queue, and choosing New from Add showed New's top level with its Refresh button; at 360×640 dark, Back from Add returns to Shows and the next Back to the sidebar. A simulated mouse back button (XTest button 8) also pops, but swallows the next click on the virtual X display, an artefact of the simulation.

**Needs a human:** the two-finger touchpad swipe and a real mouse back button, which cannot be simulated on the virtual display.
