### Rejected

- **`feed-rs` 3.0** (tried in M1). Two problems with podcast feeds: it drops an item's iTunes data (duration, season, episode, image) unless the item also has `<itunes:title>` or `<itunes:summary>`, because `MediaObject::is_not_empty` ignores those fields; and it rejects `<itunes:duration>` written as `MM:SS`. It also does not read chapters. Working around that needed a second `roxmltree` parse of every feed, so it was replaced by `rss`. The first problem is worth reporting upstream.
- **`roxmltree`**: only needed for the `feed-rs` workaround.
- **`wiremock`**: no release or commit since 2025-08-24; `httpmock` is active.

## Runtime

- **GNOME 50 runtime** (until 2026-11-09; checked in the installed `org.gnome.Platform//50`): GTK 4.22.5, libadwaita 1.9 (exports `adw_sidebar_new`, `adw_toggle_group_new`, `adw_shortcuts_dialog_new`, `adw_about_dialog_new`), GStreamer 1.26.11 with `libgstplay`, SQLite 3.50.4. Every widget in the Architecture table is available; no fallbacks needed.
- **GNOME 51 runtime** (2026-11-09, checked in the installed `org.gnome.Sdk//51`): GTK 4.24.1, libadwaita 1.10.0, GStreamer 1.28.6, GLib 2.90.1, on the freedesktop 26.08 base (rust-stable `//26.08`). Beacon stayed on GNOME 50 from 2026-10-28 only because relm4 0.11 had no `gnome_51` feature; with relm4 gone it moved, with CI on Fedora 45 (the same GTK, libadwaita and GStreamer) and the `gnome-51` Flatpak image.
- **Migrations without rusqlite_migration** (2026-11-09). It held rusqlite at 0.40 (2.6.0 requires `^0.40`), and with it `libsqlite3-sys` below 0.39, which `cargo deny` flags (RUSTSEC-2026-0459, the SQLite it bundles). Beacon used it only to apply three SQL files in order, so `store::migrate` does that itself: each change in its own transaction, counted in `PRAGMA user_version` as rusqlite_migration counted them, so libraries it made open unchanged. A library from a newer Beacon is refused (`StoreError::TooNew`) rather than used with a schema this version does not know. Beacon links the runtime's SQLite rather than the bundled one, so the advisory's fix for the SQLite actually in use comes with the GNOME runtime.
- **GNOME 51's new widgets wait for their bindings** (2026-11-09). Libadwaita 1.10 adds `adw_bind_property_to_css_class` (a style class kept in step with a property, which would replace Beacon's hand-written class toggles in `chapter_list.rs`, `play_button.rs` and `episode_row/mod.rs`) and prefix and suffix widgets on `AdwSidebar`, its items and sections; GTK 4.24 adds `GtkSvgWidget` and editable input interceptors (read from the headers in the GNOME 51 SDK). libadwaita-rs 0.9.2 binds the 1.10 additions only in its unsafe `-sys` crate, and gtk4-rs 0.11.5 has no `GtkSvgWidget`, so Beacon adopts none of them yet rather than call C directly; `MILESTONES.md` watches for the bindings.
- **No relm4** (decided by the user 2026-11-09). The app uses gtk4-rs and libadwaita-rs directly, which also took away the wait for relm4's GNOME 51 support. Each view is a GObject subclass (an `AdwBin`, or an `AdwNavigationPage` for pages pushed onto the content's navigation view), as the gtk4-rs book and GNOME Podcasts build theirs, with its layout in Rust builder code; the views keep the typed input and output enums they had (rule 4). `send` hands a view its input through a queue (`ui/messages.rs`), so input sent while it is still handling some (a widget it changes firing a signal back into it) waits its turn, as relm4 queued it; output goes to one callback its owner connects. The window (`app/object.rs`, an `AdwApplicationWindow` subclass) holds `App` and handles its messages and the results of background work in arrival order from one `async-channel`; that work runs on a tokio runtime the app owns (`app/sender.rs`). `App` keeps the window's parts and its sender as fields, rather than taking them as arguments as relm4's `update` did, and the player bar's layout change is a method (`PlayerBar::set_sheet`), since nothing about it needs to wait its turn.

## Build and packaging

- **Cargo builds, Meson installs.** Meson calls Cargo through `build-aux/cargo-build.sh` and installs the desktop file, metainfo, schema and icons. The GResource is compiled by `build.rs`, so Cargo alone can build and test.
- **Offline Flatpak build.** `build-aux/cargo-sources.json` is generated from `Cargo.lock` by `build-aux/flatpak-cargo-sources.py`, a small local script that writes the same layout as flatpak-builder-tools' generator for crates.io dependencies. It avoids downloading and running the upstream script on every update. Switch to the upstream generator if a git dependency is ever needed.
- **Sandbox permissions** start minimal (`ipc`, `wayland`, `fallback-x11`, `dri`).
  - `--share=network` (M1): fetching feeds and covers.
  - `--socket=pulseaudio` (M4): playing episodes. PulseAudio's socket is how sandboxed apps reach PipeWire; Flathub expects it for audio playback.
  - No permission for sync (M6): the app password goes through the Secret portal (`oo7`), the browser login opens through the OpenURI portal (`GtkUriLauncher`), and the server is reached over the network Beacon already has.
  - No permission for MPRIS (M4): Flatpak lets every app own `org.mpris.MediaPlayer2.{app ID}`, so `--own-name=org.mpris.MediaPlayer2.com.theoforger.Beacon`, planned in M4, was left out; `flatpak-builder-lint` flags it (`finish-args-unnecessary-appid-mpris-own-name`: "This is granted by default").

- **GNOME Podcasts** (https://gitlab.gnome.org/World/podcasts, GPL-3.0-or-later, read at commit 6717fe2 on 2026-10-30) is the model for UI elements it shares with Beacon (`CLAUDE.md` rule 13). Already aligned: the Shows grid (`GtkGridView`; since 2026-11-02 also its tiles, see below), episode rows (`GtkListBoxRow`; the cover is a cropped `GtkPicture` over a fixed-size base rather than its `GtkImage`, see Cover thumbnails), episode lists (`boxed-list` `GtkListBox`, lazy loading), the filter menu. ## Behaviour

- **Seen state on subscribe** (M1). A new subscription marks every episode seen except the newest, so subscribing to a show with 300 episodes brings one blue dot, not 300. Episodes found by later refreshes start unseen. Approved by the user on 2026-10-28.
- **Seasons come only from tags** (M1, per the requirements). Some shows put seasons only in titles ("Season 6, Ep 11 - …" in Hello From The Magic Tavern); those do not group into seasons.
- **Navigation: sections in `App`, deeper pages in an `AdwNavigationView`** (M2, decided with the user 2026-10-29). The sidebar switches sections, and `App` passes the choice on; it keeps no navigation state of its own. The content pane is a navigation view whose root page shows the section; deeper pages (Add now, podcast pages in M3) are pushed over whatever section is showing and slide in from the right. The view owns the stack and supplies Back, the two-finger touchpad swipe, the mouse's back button and Alt+Left when focus is inside it; `win.back` (Alt+Left, Back key) covers focus elsewhere. Back therefore appears only on deeper pages, never for switching sections. An earlier breadcrumb `Trail` in `App` duplicated the view's stack and was removed.
- **Episode identity** (M1). The feed's GUID; without one, the enclosure URL, then the item link, then the title. Refreshes match on this, so it must not change between fetches.
- **"New" means not seen and not played** (M3), as in the mockup: it drives the blue dot, the Shows tile badges and the sidebar counts (Shows: shows with new episodes; New: new episodes). The requirements call the tile badge "unplayed episodes"; the mockup counts new ones, which stay small, so Beacon follows the mockup. Confirmed by the user 2026-10-29.
- **New covers the last 30 days** (M3): Today, Yesterday, weekday names for two to six days ago, Last Week for seven to thirteen, Earlier in the Month for fourteen to thirty. Older episodes are only on their podcast pages. Headers use header capitalization ("Last Week", "Earlier in the Month"), unlike the mockup's sentence case. Confirmed by the user 2026-10-29, header capitalization included.
- **Podcast pages remember their sort and filters per show** (M3, migrations 002 and 003; confirmed by the user 2026-10-29).
- **Seasons**: episodes without a season tag in a show that has seasons are grouped last as "Other Episodes"; seasons follow the sort order (newest season first for Newest First).
- **Shows are sorted by title** (M3). The HIG grid-views page suggests "most recently added is often the best arrangement"; title order seemed easier for finding a show. Confirmed by the user 2026-10-29.
- **Sort and filter share one menu** (M3, asked by the user 2026-10-29), copied from GNOME Podcasts: a filter button in the podcast page's header opens three radio groups, Newest First / Oldest First, All / Played / Unplayed, All / Downloaded / Not Downloaded. Eight items, within the HIG's "between three and twelve"; it replaced a two-item sort menu (below the HIG's minimum) and then a toggle group. New uses the same button and menu (asked by the user 2026-11-01), in the content header between Search and the details toggle and only in New; its choices are the settings `new-sort`, `new-filter` and `new-downloaded`, and Oldest First reverses the recency groups. Both buttons carry GNOME Podcasts' accent dot (`filter_menu.ui`'s `circle-overlay`, here `.filter-dot`) while the list differs from the default, sort order included (asked by the user 2026-11-02); since the dot is only seen, the button's accessible description then says "Filters are on".
- **Unsubscribing asks first** (M3). It deletes the show, its episodes, progress, favourites and queue entries, so an undo toast is not possible; the HIG accepts a confirmation dialog when undo is not possible. The dialog has no default button, as the HIG asks for destructive actions.
- **The Add page takes feed addresses only until M7** (M3). M3 needs a way to subscribe for the library to be browsable end to end; searching by name (iTunes) stays in M7, and the page says so when a name is typed. Confirmed by the user 2026-10-29. Searching by name arrived in M7 (below).
- **The library is never read or written on the UI thread** (M3, after the user found filters, sorting and opening details laggy). Each change runs on a blocking worker (`AppSender::spawn_blocking`), applies its write, reloads only the parts of the views it affects, and the window applies the result; per-part request numbers drop stale results. Rows pass their episode to the details pane, which fills at once. Covers decode asynchronously (`gio::File::read_future`, `Pixbuf::from_stream_at_scale_future`) behind a placeholder.
- **Refresh** (M3) runs from the Shows and New headers, the main menu, Ctrl+R and F5. A toast reports new episodes or failed feeds; a refresh that finds nothing says nothing.
- **Show descriptions are plain text for now** (M3): `beacon_core::text::plain` drops tags and decodes entities. A stopgap: the details pane in M4 needs real rich text (paragraphs, links) and should use a maintained crate. Confirmed as a stopgap by the user 2026-10-29.

- **Playback** (M4, 2026-11-03). `beacon-core` never imports GLib and gstreamer-rs is built on it, so the rules live in core (`playback.rs`: where to resume, skip limits, the speed menu, when to save, the sleep timer and its fade, the current chapter) and the `GstPlay` wrapper in `beacon-gtk/src/player/`, reporting typed `PlayerEvent`s that `app/playback.rs` turns into store writes. An episode resumes where it was left unless it is played or was left in its last 10 seconds. The position is saved every 5 seconds of playback without reloading any view, and on pause or stop with a reload so progress bars follow; an episode played to its end is marked played and back at the start (`Store::finish`), and stays in the queue until auto-continue (M5) moves on. Video tracks are turned off: podcasts are listened to. A downloaded file plays instead of the enclosure. When the window closes, the last position is written on the main thread, the one exception to keeping store writes off it, since the window is going away. Volume and speed are GSettings keys (`volume`, `playback-rate`); a stored speed snaps to the nearest one in the menu.
- **Rich descriptions** (M4, after the user found links missing, 2026-11-03). `text::markup` turns description HTML into Pango markup: links (web and mail only), bold, italics, paragraphs, line breaks and list items, everything else escaped text, and addresses in plain text linked, as GNOME Podcasts renders episode descriptions. The details pane and the podcast page use it; GNOME Podcasts shows a show's description as plain text, Beacon links it too. Neither is selectable, as in GNOME Podcasts: a selectable label selects all its text when it takes focus. GNOME Podcasts' timestamp links, which seek, come with chapters.
- **The podcast page header follows the mockup** (M4, decided with the user 2026-11-03). It had drifted to a centred column that matched neither the mockup nor GNOME Podcasts, with no decision behind it. Now: the cover with the category, title, author, description and Unsubscribe beside it, stacking under it below 610px of page width. Sizes and spacing follow other GNOME apps (2026-11-03, after the user found the first version tight): the cover is GNOME Music's large album art, 256px, and its medium, 192px, when stacked (`ArtSize`); 32px between cover and text, as on its album page (`AlbumWidget.blp`); 6px between the text's lines, as in GNOME Software's app header (`gs-details-page.ui`); 12px above Unsubscribe and 24px above the episodes. The page measures its own width (a drawing-area probe, as grid covers do): `AdwBreakpointBin` would do this, but it does not measure height for width, which cut the wrapped description short. Departures from the mockup: More Options is in the page's header bar, not beside Unsubscribe, since the HIG's Menus page says "Secondary menus are located in the header bar, and are used to contain actions and settings for a particular view or content item", as GNOME Podcasts does; it is not round, since the HIG keeps circular buttons for "a number of smaller buttons ... in close proximity"; Unsubscribe is a normal button, since the HIG keeps pills for "a primary action for the view" and `CLAUDE.md` for the suggested action (Subscribe, M7). The category is not in capitals: the Typography page says "Do not capitalize every letter (all caps)". More Options offers Mark All as Unplayed when every episode is played (asked by the user).
- **The podcast page header keeps the cover's height** (M4, asked by the user 2026-11-03). Beside the cover, the text column fits within the cover's height: after each layout change the description loses lines (from 6) until it fits, and a Read More link on one line under it opens the whole description in an `AdwDialog` (`ui/dialogs/description.rs`). Stacked under the cover, the description stops at GNOME Podcasts' four lines (`read_more_label.rs`). Read More shows only when the description is cut short. It is a link rather than a button (asked by the user 2026-11-03), to leave the description another line; none of the HIG's pages covers links (Buttons, UI Styling, Typography, Writing Style, Accessibility, Pointer & Touch, checked). It sits under the text, not at the end of its last line, which the ellipsis would cut off. GNOME Podcasts expands the description in place; the user asked for a dialog, which keeps the header's height. The HIG's Dialogs page says a dialog should "only ever be displayed in immediate response to a deliberate user action", which Read More is. Measuring the whole description uses a large line limit, not -1: GTK hands -1 to Pango, which takes it as one line.
- **Arrow keys move between a description's links** (M4, asked by the user 2026-11-03). GTK moves between a label's links with Tab only (`gtk_label_focus`); `ui/links.rs` makes Left and Up go to the previous link and Right and Down to the next, on the details pane's description, the podcast page's and the Read More dialog's. The HIG's Keyboard page: "Where possible, arrow keys should allow moving around the UI in a directional fashion."
- **Episode covers in details, show covers in rows** (M4, decided with the user 2026-11-03), as GNOME Podcasts does: its rows load the show's cover (`episode.rs`, `set_cover`), its details the episode's own when it differs from the show's (`episode_description.rs`, `set_episode_specific_cover`). In the user's library 1,320 episodes have 333 distinct images, so episode covers in rows would mean hundreds of downloads and decodes; one cover per opened episode costs nothing noticeable. `Library::episode_cover` fetches the episode's image into the cover cache the first time its details open (the show's cover shows meanwhile, and stays when the episode has no image of its own or the show's); the player bar will show the same cover.
- **Refresh fetches four feeds at a time** (M4 sweep, 2026-11-04). `refresh_all` fetched one feed after another, so refreshing a library took the sum of every feed's wait. It now runs up to four at once (`REFRESH_AT_ONCE`): the waits overlap, and no host sees more than a few requests. The store lock is never held across a fetch. Checked by a test of four feeds that each answer after 300ms.
- **List spacing and row height follow GNOME Podcasts** (M4, asked by the user 2026-11-04). Rows: a 64px cover and content 64px tall with 6px above and below, so every row is the same height (`episode_widget.ui`: 64px cover, a 64px-tall text box, 6px margins); 6px between title and subtitle. Titles take up to two lines in any window (one line in wide windows until 2026-11-08, when the user asked for two); a row with a progress bar keeps one line, as GNOME Podcasts does (`update_progressbar_spacing`). The 64px is a minimum, so a two-line title with the body-size subtitle makes its row a couple of pixels taller. ## Custom widgets and icons

- **Queue card** (`ui/widgets/queue_card.rs`, 2026-11-10). The Queue's Next in Queue rows are one custom widget, an entry of the Queue's list view, that lays out its own `EpisodeRow`s, so a dragged row can follow the pointer inside the card and the others can slide aside, which a recycling list view cannot do (it has no move animations, and GTK drag and drop draws the dragged row as a free-floating image). libadwaita has no reorderable list. The rows keep everything else a list row has: a click, Enter or Space opens the details or selects, Up and Down move between them and on into the list, each is a list item named for screen readers. It holds every queued row rather than recycling them, which suits a queue's length; a queue of hundreds would cost what a podcast page did before its list view.
- **Episode lists are list views** (decided by the user 2026-11-08, replacing the `GtkListBox`es chosen on 2026-10-30 to follow GNOME Podcasts). The HIG: "The boxed list pattern is appropriate for relatively small static lists. … For large or dynamic lists, see list views", and "List views are an alternative to boxed lists, which are able to handle very large lists of content, as well as those with dynamic content" (Boxed Lists; List & Column Views, fetched 2026-11-08). Measured on a 2,000-episode page under Xvfb: a `GtkListBox` laid out every row it held whenever rows were added, so frames took 40ms (median) to 118ms while a page filled, rising with its length, and a resize took about 100ms; paging rows in did not help, since every row loaded stayed. Now each page is one recycling list (`ui/episode_list.rs`) over a `gio::ListStore` of entries: the page's header (a podcast page's hero), group and season headings, episodes, and the room between them, all in the one list, since only a view that scrolls itself recycles its rows (inside `AdwClampScrollable`, 900px wide as before). Scrolling at 20 to 300px a frame lays out in 4 to 8ms (median), and resizing no longer grows with the list. The list is a one-column `GtkGridView` rather than a `GtkListView` (2026-11-08, after the user found the window froze for about a second going narrow on a podcast page): a list view keeps about 200 rows whatever the window's height (205 measured at 600px), a grid view about 30 per column (33), and every row kept is restyled whenever a split view moves the page; collapsing the sidebar's split view took 250ms for one list, now 50ms. The grid is given the `List` accessible role; its items keep GTK's grid cell role, which cannot be changed. Rows also make their check box, progress bar and spinner only when first needed, and leave out the cover where it never shows. New entries replace only the ones that changed, keeping the shared start and end of the list, so a changed episode rebinds one row and the list keeps its place. Libadwaita draws only `GtkListBox` as a boxed list, so each group's rows are drawn as a card in `style.css` from the boxed list's own rules (card colours, the 1px outline, separators, 12px corners on the first and last row, the 3% and 8% hover and press shading); only the last row casts the card's soft shadow, downwards, so it does not fall across the rows above. Seasons fold under a `GtkExpander` heading as before, which takes their episodes out of the list. Departs from GNOME Podcasts (rule 13).

This reads image files the core has cached, which is rendering rather than the I/O rule 2 keeps out of the UI. Covers decode at least 2x, since a widget not yet on screen reports scale 1. A `GtkPicture` takes its natural size from the texture's pixel count, so a 2x texture once doubled a cover's size on HiDPI screens (found by the user on one Hello From The Magic Tavern episode, 2026-10-30); covers then used a fixed-size `GtkImage`. That letterboxed art that is not square into a strip, so since 2026-11-02 a cover is an overlay whose base child sets the size (a fixed-size box, or `covers::square` in the Shows grid) with the art as a `GtkPicture` overlay (`ContentFit::Cover`, cropped to the square). Overlay children never set the overlay's size, so the 2x texture cannot grow the layout (checked at scale 2). The decoder reads the image's size first and scales its shorter side to the target, so cropping never scales up. Grid covers (2026-11-03) are decoded at exactly the device pixels their column draws (the surface's scale, so fractional scaling too). Rounding the size up to a multiple of 8 had them drawn a few percent smaller than decoded, which kept them soft (found by the user; against a Lanczos resize of the source, 27.9 dB rounded, 37.8 dB exact). GNOME Podcasts gets there differently: Lanczos3 thumbnails at 64 to 512px (`thumbnail_generator.rs`) drawn unscaled when they fit (`ContentFit::ScaleDown`). Finishing a 2x decode with gdk-pixbuf's `Hyper` scaler measured worse (35.1 dB) than one exact decode, so decoding stays one pass, on a GIO worker thread, first when allocated and again 150ms after the window stops resizing; the old art stays up meanwhile, and a grid cover's new size replaces the old texture in the cache. Covers being decoded are shared: a long list asked for one show's cover once per row, decoding a 3000px image up to ten times at startup. Decoding and the cache live in `ui/cover_cache.rs`. The cache keeps up to 64MB of pixels, least recently used dropped first (M4 sweep, 2026-11-04): with episodes' own covers in the details pane and the player bar, it would otherwise grow with every episode opened.

- **Downloads** (M5, 2026-11-10). Only ever when asked: a row's menu or the details pane's More Options (Download, then Cancel Download while it runs, then Delete Download), selection mode's Download (the selected episodes not yet downloaded), or a podcast page's Download All Episodes, which asks first in an `AdwAlertDialog` ("Download 40 Episodes?", Download suggested and the default) since it can fill a disk. Files go to the data folder (`beacon/downloads/ID.ext`, the extension from the audio type the server names, else the address), which the sandbox already allows, so no new permission. GNOME Podcasts' downloader (`downloader.rs`) writes a temporary file and renames it when done, and starts over every time; Beacon writes `ID.part` beside the final file and, when a download stopped part way (the connection dropped, Beacon closed), asks for the rest with an HTTP range request, starting over when the server sends the whole file instead. Cancelling deletes the part. Three download at once and the rest wait their turn, so Download All Episodes does not open a connection per episode; the download client has a connect and a read timeout but no limit on the whole request, which the feed client's 60 seconds would be for an hour of audio. As in GNOME Podcasts (`download_progress_bar.rs`), a downloading row shows a progress bar under its subtitle, labelled Download Progress for screen readers, in place of the playback progress while it shows; GNOME Podcasts also puts a Cancel button on the row and the size so far beside the subtitle, where Beacon keeps the row to its two controls and offers Cancel Download in the menu. Deleting one download is not confirmed (it can be downloaded again, as in GNOME Podcasts); Delete All Downloads is. A failed download says why in a toast naming the episode, one message per `DownloadError` variant; a cancelled one says nothing.

- **Preloading the next episode** (asked by the user 2026-11-08). `GstPlay` holds one stream, so the player keeps two: the one playing, and one that opens the next episode (the queue's first, else the list's next) paused, which buffers its start. Playing that episode swaps them, so it starts at once from where it was left, and the length the waiting one learned is reported then; only the playing one's events are reported at all, and a preload that fails is only not preloaded. It starts once the playing episode has first finished buffering, so the two never compete for the connection, follows "up next" as the queue changes, and is skipped on a metered connection (`GNetworkMonitor`, through the network portal in the sandbox, no new permission), where it would spend data on an episode that may never play. A downloaded episode preloads from its file.
- **Buffering whole episodes** (asked by the user 2026-11-09). Each `GstPlay`'s playbin gets the `download` flag, so a stream is buffered to a file as a whole rather than a few seconds ahead: the seek bar can show how far it got, seeking back is instant, and a dropped connection does not stop what is held. The file goes under the cache folder (`beacon/buffer`), not the temporary folder, which is often in memory, and is removed as it is opened (queue2's `temp-remove`). How far it got comes from a buffering query every half second, as the share of the stream up to the end of the stretch the position is in (`player/buffering.rs`); the seek bar shows it as the stock `GtkRange` fill level, which Adwaita styles, with seeking past it still allowed. GTK reallocates the scale but not its trough when the level changes, so the bar queues the trough's allocation itself (checked in `ui/display_tests.rs`). The next episode is preloaded once all of the playing one is held, rather than once it first plays, so the two never compete for the connection. The episode restored at launch is opened paused and starts buffering at once, unless the connection is metered (a downloaded one always); its buffering shows as paused, and an error waits until it is played. `gio::NetworkMonitor` changes start what was held back, or drop the preload, when the connection becomes metered or not.
- **Sync** (M6, 2026-11-10; `docs/specs/sync.md`). The engine is in core (`beacon_core::sync`): the gpodder payloads and the `SyncBackend` trait (`sync/mod.rs`), nextcloud-gpodder and the Nextcloud logins (`sync/nextcloud.rs`), the keyring (`sync/keyring.rs`) and one sync (`sync/service.rs`); the store's side is `store/sync.rs` with migration 004's triggers. The window runs it (`app/sync/`). Decisions made while building it:
  - **Pushed actions are never dated before the sync's fetch** (found against nc-gpodder-lite, which filters as nextcloud-gpodder does: `timestamp_epoch > since`, the action's own time). An action dated when the change happened, sent 30 seconds later after a pause, was older than the `since` another device had just been given, and never reached it. Each action is dated the later of its change and the server's time when this sync fetched; each `since` reaches back one second before the server's time, so a change sent in the same second is not missed, and an action seen twice changes nothing (`Applied::Same`).
  - **Made-up GUIDs are not sent** (the spec's open question 2). Beacon's fallback for a missing GUID is the enclosure URL (an episode without audio is never synced), so `guid` is sent only when it differs from the enclosure URL; incoming actions match a stored GUID or the enclosure URL.
  - **Marking unplayed is not synced** (open question 1, left as the spec has it): it records nothing and drops a pending play, so it is not undone by the next sync's push either. Reset Progress is sent, as a play at 0.
  - **Triggers record only while the Sync switch is on**, as the spec says; changes made with it off are not sent when it is turned back on. A guard row (`sync_guard`) silences them while changes from the server are written (`Store::quietly`); every open of the library lifts it, so a crash cannot leave it set.
  - **A pending local subscription change beats the server's** (a remove the server still lists as added, or the reverse): both happened since the last sync, and keeping the local one loses nothing.
  - **Quit closes the window** (Ctrl+Q and the app's quit), so the window's state is saved and the last sync runs: `g_application_quit` closed nothing and saved nothing. Closing hides the window, pauses, syncs for up to five seconds, then closes.
  - **The Sync page** (`ui/dialogs/sync_page.rs`) has GNOME Podcasts' rows (`sync_preferences.ui`, read at commit a3f48c6): server, Log In With as an `AdwToggleGroup` (Browser / Password), username, password, a pill Log In, a spinner with a label while it waits; signed in, the account, the Sync switch and Last Synced. It departs in three ways: Log In is `suggested-action` (the page's one primary action; the HIG's Buttons page, "Pill can be used when a text button is situated in open space, and is a primary action for the view"); Log Out is an `AdwButtonRow` under the account rather than a destructive button in a header of its own, since the page sits in the Preferences dialog (Boxed Lists: "Pill buttons are used when there is a single action which requires attention or delineation from the content above. In other cases, button rows are generally used"); and Sync Now is a plain button on the Last synced row, which activates it, rather than a second pill, keeping pills to the suggested action. The account shows as one row (user, server as subtitle) rather than two read-only entry rows. Field labels (Server address, Log in with, Last synced) use sentence capitalization (Writing Style: "Sentence capitalization should be used for labels that form sentences or that run on to other text, including … text entry boxes, field labels"). The waiting state has Cancel, which GNOME Podcasts lacks. The page's icon is `network-server-symbolic`; Adwaita has no sync icon.
  - **Sync toasts go to Preferences while it is open** (2026-11-12, found in the M6 screenshots): a narrow window's Preferences is a bottom sheet over the window's toasts, so a failed login said nothing visible. `App::sync_toast` uses the dialog's own toast overlay.
  - **An unreadable keyring keeps the account signed in** (2026-11-12): the page shows the account, launch says the keyring is not available, and Sync Now says it again; before, the page showed the login form while the library still held the account.
  - **Errors**: each `SyncError` has its own message (`ui/errors.rs`). Sync Now, logging in and the first sync show every one; a sync nobody asked for shows only those the user can fix (unauthorized, app missing, keyring) and logs the rest.
