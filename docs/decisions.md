### Rejected

- **`feed-rs` 3.0** (tried in M1). Two problems with podcast feeds: it drops an item's iTunes data (duration, season, episode, image) unless the item also has `<itunes:title>` or `<itunes:summary>`, because `MediaObject::is_not_empty` ignores those fields; and it rejects `<itunes:duration>` written as `MM:SS`. It also does not read chapters. Working around that needed a second `roxmltree` parse of every feed, so it was replaced by `rss`. The first problem is worth reporting upstream.
- **`roxmltree`**: only needed for the `feed-rs` workaround.
- **`wiremock`**: no release or commit since 2025-08-24; `httpmock` is active.

## Build and packaging

- **Cargo builds, Meson installs.** Meson calls Cargo through `build-aux/cargo-build.sh` and installs the desktop file, metainfo, schema and icons. The GResource is compiled by `build.rs`, so Cargo alone can build and test.
- **Offline Flatpak build.** `build-aux/cargo-sources.json` is generated from `Cargo.lock` by `build-aux/flatpak-cargo-sources.py`, a small local script that writes the same layout as flatpak-builder-tools' generator for crates.io dependencies. It avoids downloading and running the upstream script on every update. Switch to the upstream generator if a git dependency is ever needed.
- **Sandbox permissions** start minimal (`ipc`, `wayland`, `fallback-x11`, `dri`).
  - `--share=network` (M1): fetching feeds and covers.
  - `--socket=pulseaudio` (M4): playing episodes. PulseAudio's socket is how sandboxed apps reach PipeWire; Flathub expects it for audio playback.
  - No permission for MPRIS (M4): Flatpak lets every app own `org.mpris.MediaPlayer2.{app ID}`, so `--own-name=org.mpris.MediaPlayer2.com.theoforger.Beacon`, planned in M4, was left out; `flatpak-builder-lint` flags it (`finish-args-unnecessary-appid-mpris-own-name`: "This is granted by default").

## Behaviour

- **Seen state on subscribe** (M1). A new subscription marks every episode seen except the newest, so subscribing to a show with 300 episodes brings one blue dot, not 300. Episodes found by later refreshes start unseen. Approved by the user on 2026-10-28.
- **Seasons come only from tags** (M1, per the requirements). Some shows put seasons only in titles ("Season 6, Ep 11 - …" in Hello From The Magic Tavern); those do not group into seasons.
- **Navigation: sections in `App`, deeper pages in an `AdwNavigationView`** (M2, decided with the user 2026-10-29). The sidebar switches sections, and `App` passes the choice on; it keeps no navigation state of its own. The content pane is a navigation view whose root page shows the section; deeper pages (Add now, podcast pages in M3) are pushed over whatever section is showing and slide in from the right. The view owns the stack and supplies Back, the two-finger touchpad swipe, the mouse's back button and Alt+Left when focus is inside it; `win.back` (Alt+Left, Back key) covers focus elsewhere. Back therefore appears only on deeper pages, never for switching sections. An earlier breadcrumb `Trail` in `App` duplicated the view's stack and was removed.
- **Episode identity** (M1). The feed's GUID; without one, the enclosure URL, then the item link, then the title. Refreshes match on this, so it must not change between fetches.
- **"New" means not seen and not played** (M3), as in the mockup: it drives the blue dot, the Shows tile badges and the sidebar counts (Shows: shows with new episodes; New: new episodes). The requirements call the tile badge "unplayed episodes"; the mockup counts new ones, which stay small, so Beacon follows the mockup. Confirmed by the user 2026-10-29.
- **New covers the last 30 days** (M3): Today, Yesterday, weekday names for two to six days ago, Last Week for seven to thirteen, Earlier in the Month for fourteen to thirty. Older episodes are only on their podcast pages. Headers use header capitalization ("Last Week", "Earlier in the Month"), unlike the mockup's sentence case. Confirmed by the user 2026-10-29, header capitalization included.
- **Podcast pages remember their sort and filters per show** (M3, migrations 002 and 003; confirmed by the user 2026-10-29).
- **Seasons**: episodes without a season tag in a show that has seasons are grouped last as "Other Episodes"; seasons follow the sort order (newest season first for Newest First).
- **Shows are sorted by title** (M3). The HIG grid-views page suggests "most recently added is often the best arrangement"; title order seemed easier for finding a show. Confirmed by the user 2026-10-29.
- **Sort and filter share one menu** (M3, asked by the user 2026-10-29), copied from GNOME Podcasts: a filter button in the podcast page's header opens three radio groups, Newest First / Oldest First, All / Played / Unplayed, All / Downloaded / Not Downloaded. Eight items, within the HIG's "between three and twelve"; it replaced a two-item sort menu (below the HIG's minimum) and then a toggle group. Downloads arrive in M5; until then everything counts as not downloaded. New uses the same button and menu (asked by the user 2026-11-01), in the content header between Search and the details toggle and only in New; its choices are the settings `new-sort`, `new-filter` and `new-downloaded`, and Oldest First reverses the recency groups. Both buttons carry GNOME Podcasts' accent dot (`filter_menu.ui`'s `circle-overlay`, here `.filter-dot`) while the list differs from the default, sort order included (asked by the user 2026-11-02); since the dot is only seen, the button's accessible description then says "Filters are on".
- **Unsubscribing asks first** (M3). It deletes the show, its episodes, progress, favourites and queue entries, so an undo toast is not possible; the HIG accepts a confirmation dialog when undo is not possible. The dialog has no default button, as the HIG asks for destructive actions.
- **The Add page takes feed addresses only until M7** (M3). M3 needs a way to subscribe for the library to be browsable end to end; searching by name (iTunes) stays in M7, and the page says so when a name is typed. Confirmed by the user 2026-10-29.
- **The library is never read or written on the UI thread** (M3, after the user found filters, sorting and opening details laggy). Each change runs on a blocking worker (`spawn_oneshot_command`), applies its write, reloads only the parts of the views it affects, and the window applies the result; per-part request numbers drop stale results. Rows pass their episode to the details pane, which fills at once. Covers decode asynchronously (`gio::File::read_future`, `Pixbuf::from_stream_at_scale_future`) behind a placeholder.
- **Refresh** (M3) runs from the Shows and New headers, the main menu, Ctrl+R and F5. A toast reports new episodes or failed feeds; a refresh that finds nothing says nothing.
- **Show descriptions are plain text for now** (M3): `beacon_core::text::plain` drops tags and decodes entities. A stopgap: the details pane in M4 needs real rich text (paragraphs, links) and should use a maintained crate. Confirmed as a stopgap by the user 2026-10-29.

- **Playback** (M4, 2026-11-03). `beacon-core` never imports GLib and gstreamer-rs is built on it, so the rules live in core (`playback.rs`: where to resume, skip limits, the speed menu, when to save, the sleep timer and its fade, the current chapter) and the `GstPlay` wrapper in `beacon-gtk/src/player/`, reporting typed `PlayerEvent`s that `app/playback.rs` turns into store writes. An episode resumes where it was left unless it is played or was left in its last 10 seconds. The position is saved every 5 seconds of playback without reloading any view, and on pause or stop with a reload so progress bars follow; an episode played to its end is marked played and back at the start (`Store::finish`), and stays in the queue until auto-continue (M5) moves on. Video tracks are turned off: podcasts are listened to. A downloaded file plays instead of the enclosure. When the window closes, the last position is written on the main thread, the one exception to keeping store writes off it, since the window is going away. Volume and speed are GSettings keys (`volume`, `playback-rate`); a stored speed snaps to the nearest one in the menu.
- **Rich descriptions** (M4, after the user found links missing, 2026-11-03). `text::markup` turns description HTML into Pango markup: links (web and mail only), bold, italics, paragraphs, line breaks and list items, everything else escaped text, and addresses in plain text linked, as GNOME Podcasts renders episode descriptions. The details pane and the podcast page use it; GNOME Podcasts shows a show's description as plain text, Beacon links it too. Neither is selectable, as in GNOME Podcasts: a selectable label selects all its text when it takes focus. GNOME Podcasts' timestamp links, which seek, come with chapters.
- **The podcast page header follows the mockup** (M4, decided with the user 2026-11-03). It had drifted to a centred column that matched neither the mockup nor GNOME Podcasts, with no decision behind it. Now: the cover with the category, title, author, description and Unsubscribe beside it, stacking under it below 610px of page width. Sizes and spacing follow other GNOME apps (2026-11-03, after the user found the first version tight): the cover is GNOME Music's large album art, 256px, and its medium, 192px, when stacked (`ArtSize`); 32px between cover and text, as on its album page (`AlbumWidget.blp`); 6px between the text's lines, as in GNOME Software's app header (`gs-details-page.ui`); 12px above Unsubscribe and 24px above the episodes. The page measures its own width (a drawing-area probe, as grid covers do): `AdwBreakpointBin` would do this, but it does not measure height for width, which cut the wrapped description short. Departures from the mockup: More Options is in the page's header bar, not beside Unsubscribe, since the HIG's Menus page says "Secondary menus are located in the header bar, and are used to contain actions and settings for a particular view or content item", as GNOME Podcasts does; it is not round, since the HIG keeps circular buttons for "a number of smaller buttons ... in close proximity"; Unsubscribe is a normal button, since the HIG keeps pills for "a primary action for the view" and `CLAUDE.md` for the suggested action (Subscribe, M7). The category is not in capitals: the Typography page says "Do not capitalize every letter (all caps)". More Options offers Mark All as Unplayed when every episode is played (asked by the user).
- **The podcast page header keeps the cover's height** (M4, asked by the user 2026-11-03). Beside the cover, the text column fits within the cover's height: after each layout change the description loses lines (from 6) until it fits, and a Read More link on one line under it opens the whole description in an `AdwDialog` (`ui/dialogs/description.rs`). Stacked under the cover, the description stops at GNOME Podcasts' four lines (`read_more_label.rs`). Read More shows only when the description is cut short. It is a link rather than a button (asked by the user 2026-11-03), to leave the description another line; none of the HIG's pages covers links (Buttons, UI Styling, Typography, Writing Style, Accessibility, Pointer & Touch, checked). It sits under the text, not at the end of its last line, which the ellipsis would cut off. GNOME Podcasts expands the description in place; the user asked for a dialog, which keeps the header's height. The HIG's Dialogs page says a dialog should "only ever be displayed in immediate response to a deliberate user action", which Read More is. Measuring the whole description uses a large line limit, not -1: GTK hands -1 to Pango, which takes it as one line.
- **Arrow keys move between a description's links** (M4, asked by the user 2026-11-03). GTK moves between a label's links with Tab only (`gtk_label_focus`); `ui/links.rs` makes Left and Up go to the previous link and Right and Down to the next, on the details pane's description, the podcast page's and the Read More dialog's. The HIG's Keyboard page: "Where possible, arrow keys should allow moving around the UI in a directional fashion."
- **Episode covers in details, show covers in rows** (M4, decided with the user 2026-11-03), as GNOME Podcasts does: its rows load the show's cover (`episode.rs`, `set_cover`), its details the episode's own when it differs from the show's (`episode_description.rs`, `set_episode_specific_cover`). In the user's library 1,320 episodes have 333 distinct images, so episode covers in rows would mean hundreds of downloads and decodes; one cover per opened episode costs nothing noticeable. `Library::episode_cover` fetches the episode's image into the cover cache the first time its details open (the show's cover shows meanwhile, and stays when the episode has no image of its own or the show's); the player bar will show the same cover.
- **Refresh fetches four feeds at a time** (M4 sweep, 2026-11-04). `refresh_all` fetched one feed after another, so refreshing a library took the sum of every feed's wait. It now runs up to four at once (`REFRESH_AT_ONCE`): the waits overlap, and no host sees more than a few requests. The store lock is never held across a fetch. Checked by a test of four feeds that each answer after 300ms.
- **List spacing and row height follow GNOME Podcasts** (M4, asked by the user 2026-11-04). Rows: a 64px cover and content 64px tall with 6px above and below, so every row is the same height (`episode_widget.ui`: 64px cover, a 64px-tall text box, 6px margins); 6px between title and subtitle. Titles take up to two lines in any window (one line in wide windows until 2026-11-08, when the user asked for two); a row with a progress bar keeps one line, as GNOME Podcasts does (`update_progressbar_spacing`). The 64px is a minimum, so a two-line title with the body-size subtitle makes its row a couple of pixels taller. Lists: in New, 32px above and below, groups 24px apart and each heading 6px above its list (`home_episode_list.ui`); on a podcast page, 32px above the header (`show_widget.ui`) and seasons 24px apart. In the narrow layout the podcast page header is centred under its cover (asked by the user).
- **Long lists were paged** (M4, after the user found opening shows and details slow, 2026-11-03; replaced 2026-11-08 by list views, below). With 607 episodes in one show, every row's layout was redone on each change; rows then came 40 at a time as the list was scrolled, at most 8ms of work per turn, and reloads rebound only changed rows. The Shows grid skips unchanged cards. The row Play button is square like the menu button beside it (asked by the user).
- **Sleep timer, volume and speed** (M4, settled by the user 2026-11-03; open question 2). GNOME Podcasts has no sleep timer or volume control, so these follow the mockup and the user's choices:
  - The Sleep Timer button opens a menu: Off, 15, 30, 45 and 60 minutes, and End of Episode. When the timer runs out, playback fades out over about 5 seconds and pauses, keeping its position.
  - The volume slider sets Beacon's own audio stream volume, the per-app volume GNOME Settings shows, and it is remembered across restarts.
  - Playback speed follows GNOME Podcasts (`player_rate.ui`, commit 63b82e7) rather than the mockup's click-to-cycle button: a menu button with 0.75×, 0.90×, 1.00×, 1.25×, 1.50×, 1.75× and 2.00×, labelled with the current rate.

- **The player bar** (M4, 2026-11-04). Built from what GNOME Podcasts' player uses (`player_small.ui`, `player_big.ui`): the playing episode is a flat button with its cover, title (`caption-heading`) and show (`caption`) that opens its details; the transport controls are flat circular buttons; the seek bar is a `GtkScale` without its value, with elapsed and remaining time beside it; speed is its rate menu. From the mockup and the requirements: Favourite before Back 10 Seconds (Chapters since 2026-11-08, below), a neutral round Play and Pause (the one filled control), Forward 30 Seconds (GNOME Podcasts skips forward 10), Next Episode, the sleep timer and volume. The cover is the episode's own, as in the details pane. In the narrow layout the bar stacks and leaves out speed, sleep timer and volume, as the mockup does. The HIG's Sliders page: "in video players, it is common to situate a horizontal seek bar along the bottom of the window ... simply placing a slider in this position is enough to identify it", and "use a text label or icon to identify the slider", which the volume slider's speaker icon does; Buttons: circular buttons "can be useful in situations where a number of smaller buttons are positioned in close proximity". The sleep timer's dot is the filter button's, said in its accessible description too. A row's Play shows Pause while its episode plays.
- **Chapters in the player bar** (asked by the user 2026-11-08, in place of the bar's Favourite, which stays in the details pane and row menus). A Chapters button (`view-list-ordered-symbolic`; New has the bulleted list) opens a popover listing the playing episode's chapters as the details pane does (start time and title, the one playing grey with its time in the accent colour, `ui/chapter_list.rs`); choosing one seeks to it. Unavailable, with the tooltip "No Chapters", while the episode has none, so the transport keeps its place. A popover, not a menu or a page: Popovers gives "a list of content items that can be opened" as popover content and asks that they "should not cover more than a third of their parent window", so the list scrolls past 320px; Menus says "Menus should contain between three and twelve items", and episodes often have more chapters. GNOME Podcasts pushes a Chapters page from its player (`chapters.ui`, `player_big.ui`'s chapters button), a departure from rule 13 that keeps the player and what is behind it in view. The seek bar marks each chapter's start with a tick below it (`GtkScale` marks), as Sliders suggests: "In some cases, it is helpful to mark significant values along the length of the slider with text or tick marks." The chapters load when an episode starts playing (the same fetch the details pane uses, kept once fetched). The bar's height no longer animates between Nothing Playing and the player, which made GTK warn that it was given less height than it needed.

- **The details pane** (M4, 2026-11-04). - **JSON chapters are fetched when first shown** (M4, 2026-11-04). - **Selection mode in episode lists** (M4, asked by the user 2026-11-04; how it starts and its actions chosen by the user). A secondary click or a long press selects a row, but rows show no check box on hover: the row's More Options menu has Select instead, after Show Details, which selects that episode (decided by the user 2026-11-04, after trying the hover check box). On a page narrower than 520sp (an `AdwBreakpointBin` measures the page, so a page squeezed by the details pane counts) they fold into one Selection Actions menu, since four icons, Cancel, the count and the close button do not fit in 360px. - **Media keys through MPRIS** (M4, 2026-11-04), as GNOME Podcasts does it. Beacon answers Play, Pause, Play/Pause, Stop, Next, Seek, SetPosition and Raise, and shows the episode (title, the show as artist and album, length, the episode's own cover as a file URI) with its status and position. - **Play buttons show loading** (asked by the user 2026-11-07, refined the same day). Wide: an `AdwToolbarView` with the player bar at the bottom. ## Custom widgets and icons

- **Episode lists are list views** (decided by the user 2026-11-08, replacing the `GtkListBox`es chosen on 2026-10-30 to follow GNOME Podcasts). The HIG: "The boxed list pattern is appropriate for relatively small static lists. … For large or dynamic lists, see list views", and "List views are an alternative to boxed lists, which are able to handle very large lists of content, as well as those with dynamic content" (Boxed Lists; List & Column Views, fetched 2026-11-08). Measured on a 2,000-episode page under Xvfb: a `GtkListBox` laid out every row it held whenever rows were added, so frames took 40ms (median) to 118ms while a page filled, rising with its length, and a resize took about 100ms; paging rows in did not help, since every row loaded stayed. Now each page is one recycling list (`ui/episode_list.rs`) over a `gio::ListStore` of entries: the page's header (a podcast page's hero), group and season headings, episodes, and the room between them, all in the one list, since only a view that scrolls itself recycles its rows (inside `AdwClampScrollable`, 900px wide as before). Scrolling at 20 to 300px a frame lays out in 4 to 8ms (median), and resizing no longer grows with the list. The list is a one-column `GtkGridView` rather than a `GtkListView` (2026-11-08, after the user found the window froze for about a second going narrow on a podcast page): a list view keeps about 200 rows whatever the window's height (205 measured at 600px), a grid view about 30 per column (33), and every row kept is restyled whenever a split view moves the page; collapsing the sidebar's split view took 250ms for one list, now 50ms. The grid is given the `List` accessible role; its items keep GTK's grid cell role, which cannot be changed. Rows also make their check box, progress bar and spinner only when first needed, and leave out the cover where it never shows. New entries replace only the ones that changed, keeping the shared start and end of the list, so a changed episode rebinds one row and the list keeps its place. Libadwaita draws only `GtkListBox` as a boxed list, so each group's rows are drawn as a card in `style.css` from the boxed list's own rules (card colours, the 1px outline, separators, 12px corners on the first and last row, the 3% and 8% hover and press shading); only the last row casts the card's soft shadow, downwards, so it does not fall across the rows above. Seasons fold under a `GtkExpander` heading as before, which takes their episodes out of the list. Departs from GNOME Podcasts (rule 13).
- **Shows grid tiles follow GNOME Podcasts** (M3, after the user saw the gaps and the badge move as the window resized, 2026-11-02). Read at commit 63b82e7 (`widgets/shows_view.rs`, `style.css`'s `.shows-grid`): 2 to 7 columns, a 6px margin on every tile and 6px of padding on the grid, and covers that fill their column and stay square (a `GtkPicture`, measured height for width, with the grid's `vscroll-policy` natural). The gaps stay the same and the covers grow, from 150px. Beacon departs in three ways: the title and author under each cover and the new-episode badge come from the mockup, the badge sits on the cover so it keeps to its corner, and the grid keeps its 1200px clamp (the HIG's maximum width) where GNOME Podcasts clamps at seven 268px columns. A non-square cover is cropped to the square (`ContentFit::Cover`) rather than letterboxed.
- **A ring around the new-episode badge** (M3, 2026-11-02). The badge keeps the mockup's accent colour, which vanished on a cover of the same colour. A 2px ring in `--window-bg-color` separates it from any cover, in light, dark and high contrast.
- **Add's search field takes focus when the page opens** (M3, 2026-11-02), from the navigation page's `shown` signal: the page is one field, and before this, typed text went nowhere until it was clicked.
- **Reset in the filter menu** (M3, asked by the user 2026-11-02). A last section with Reset Sort and Filters returns to Newest First, All, All. It is available only while the accent dot shows. GNOME Podcasts has no Reset; this departs from it.
- **Row menus are built when opened** (M3, 2026-11-03), as GNOME Podcasts builds its `PopoverMenu` in `EpisodeWidget::init_context_menu` (`episode.rs`, commit 63b82e7). A `GtkMenuButton` given a menu model builds the whole popover at once; doing that for every row was most of a row's cost (607 rows of one feed). Beacon keeps its More Options button and fills it from `set_create_popup_func`, dropping the model when the row is rebound so the wording follows the episode's state.
- **Played titles are dimmed** (M3, asked by the user 2026-11-03), as GNOME Podcasts does: `EpisodeWidget::set_played` adds `dim-label` to the title and shows the checkmark (`episode.rs`, commit 63b82e7).
- **Refresh always reports** (M3, asked by the user 2026-11-03): "No new episodes" when nothing was found, besides the count of new episodes or failed podcasts. GNOME Podcasts shows no toast after a refresh; this departs from it.
- **Shows grid spacing is padding, not margin** (M3, 2026-11-03). GNOME Podcasts gives each cell `margin: 6px; padding: 0`; its cells are bare covers. Beacon's tiles carry a title and author, and libadwaita draws the keyboard focus ring 2px inside the cell (`gridview > child:focus-visible { outline-offset: -2px }`), so with no padding the ring cut through the text (found by the user). Cells get `padding: 6px; margin: 0` instead: the same 12px gaps, the ring around the tile, and the mockup's hover highlight around it (`.showcard { padding: 8px }` there).
- **`SmoothTexture`** (`ui/widgets/smooth_texture.rs`, M3, 2026-11-03), a `GdkPaintable` that draws a texture with `gtk::Snapshot::append_scaled_texture` and `gsk::ScalingFilter::Trilinear`. `GtkPicture` and `GtkImage` draw textures with a linear filter, which turns soft and jagged when a texture is drawn much smaller than its pixels. It first stood in for decoding grid covers at their drawn size; the user still found them softer than the details pane's, since trilinear filtering blends mipmap levels. Grid covers are now decoded at the device pixels they are drawn at (see Cover thumbnails), and the paintable keeps a cover clean while a resize waits for the new decode. No stock widget sets the filter.
- **Episode lists after the accessibility checkpoint** (2026-11-03). Tab visits the focused row's buttons and then leaves the list (`tab-behavior` set to `ITEM`, on the list view since 2026-11-08; the default walked every row of a long feed), as GNOME Podcasts sets on its Shows grid; the arrow keys move between rows. Each list was named after its recency group or season; since 2026-11-08 a page has one list, named "Episodes" on a podcast page and "New Episodes" in New, with the group and season headings in it as headings. Rows have an accessible name: the title, "New" and "Played" when they apply, and the subtitle with commas instead of " · ", which Orca read as "middle dot" (the divider is a bullet, " • ", since 2026-11-08, asked by the user; Orca would read it as "bullet") (naming only the subtitle label did not help: Orca reads an unnamed row from its text). Since 2026-11-08 the name is on the list item, which is what takes focus. The dot, title, check and subtitle have the `Presentation` role, which keeps them out of the accessibility tree; exposed, they were read again after the name. The `Hidden` state did not work for this, since GTK sets it from the widget's visibility.
- **No show name or cover in a podcast page's rows** (asked by the user 2026-11-03 and 2026-11-04): the page is the show's, so its rows' subtitles start with the season and episode or the date, and they have no cover. New keeps both. GNOME Podcasts shows the cover on every row, its show page included (`EpisodeWidget::init`); this departs from it.
- **The filter menu's groups have titles** (2026-11-03): Order, Progress and Downloads, so the two "All" items can be told apart; Orca read both as "All". GNOME Podcasts' `filter_menu.ui` has untitled sections; this departs from it.
- **Escape on the Add page** (2026-11-03): a `GtkSearchEntry` keeps Escape for itself, so Escape in Add's field clears it, and in the empty field leaves the page, as Escape does elsewhere.
- **Keyboard focus and Back** (2026-11-03). Focus starts in the sidebar. A row opening the details pane moves focus into the pane; Escape closes it, and closing it returns focus to the row. Alt+Left and the Back key also close the narrow details page, and in the narrow layout return from the content to the sidebar, as Escape does.
- **`EpisodeRow`** (`ui/widgets/episode_row/`, M3), an `AdwBin` subclass (a `GtkListBoxRow` one until 2026-11-08) holding its parts (cover, dot, title, check, subtitle, progress, play button, row menu), like GNOME Podcasts' `PdEpisode`. Keeping the parts lets the list view bind a row to another episode as it scrolls.
- **Cover thumbnails** (`ui/covers.rs`, M3). Covers can be thousands of pixels wide, so each is decoded once with `gdk-pixbuf` at the size it is drawn and kept, then wrapped in a `GdkMemoryTexture` (`gdk::Texture::for_pixbuf` is deprecated since GTK 4.20). This reads image files the core has cached, which is rendering rather than the I/O rule 2 keeps out of the UI. Covers decode at least 2x, since a widget not yet on screen reports scale 1. A `GtkPicture` takes its natural size from the texture's pixel count, so a 2x texture once doubled a cover's size on HiDPI screens (found by the user on one Hello From The Magic Tavern episode, 2026-10-30); covers then used a fixed-size `GtkImage`. That letterboxed art that is not square into a strip, so since 2026-11-02 a cover is an overlay whose base child sets the size (a fixed-size box, or `covers::square` in the Shows grid) with the art as a `GtkPicture` overlay (`ContentFit::Cover`, cropped to the square). Overlay children never set the overlay's size, so the 2x texture cannot grow the layout (checked at scale 2). The decoder reads the image's size first and scales its shorter side to the target, so cropping never scales up. Grid covers (2026-11-03) are decoded at exactly the device pixels their column draws (the surface's scale, so fractional scaling too). Rounding the size up to a multiple of 8 had them drawn a few percent smaller than decoded, which kept them soft (found by the user; against a Lanczos resize of the source, 27.9 dB rounded, 37.8 dB exact). GNOME Podcasts gets there differently: Lanczos3 thumbnails at 64 to 512px (`thumbnail_generator.rs`) drawn unscaled when they fit (`ContentFit::ScaleDown`). Finishing a 2x decode with gdk-pixbuf's `Hyper` scaler measured worse (35.1 dB) than one exact decode, so decoding stays one pass, on a GIO worker thread, first when allocated and again 150ms after the window stops resizing; the old art stays up meanwhile, and a grid cover's new size replaces the old texture in the cache. Covers being decoded are shared: a long list asked for one show's cover once per row, decoding a 3000px image up to ten times at startup. Decoding and the cache live in `ui/cover_cache.rs`. The cache keeps up to 64MB of pixels, least recently used dropped first (M4 sweep, 2026-11-04): with episodes' own covers in the details pane and the player bar, it would otherwise grow with every episode opened.

- **Resizing stays cheap with long descriptions** (found by the user 2026-11-08: Destination Linux's page lagged while the window was dragged, Hey Riddle Riddle's did not). - **What plays next** (M5). As the mockup's `autoNext` and `advance`, in `beacon_core::queue`: the manual queue first, then the episodes after the playing one in the list it was started from (New, a podcast page; Favorites and Downloaded once they exist), minus the queued ones, or that whole list when the playing episode has left it. The list is read again in its view's order and filters when needed, rather than remembered, so what follows is what the list shows now. Starting an episode takes it off the queue and clears its blue dot (the mockup's `playEp`), so Now Playing is never also in Next in Queue. Rows in the Queue view keep the list as it was, as the mockup's queue rows have no list of their own; the details pane's Play uses the list it was opened from. Next from the list shows ten, as the mockup does. Played episodes are not skipped, also as the mockup. A sleep timer set to End of Episode stops instead. The list and the last episode played are kept in settings (`play-source`, `last-episode`), so after a restart, with nothing playing, Next from carries on after the last episode played, as do Next and auto-continue (found missing by the user 2026-11-08). The player bar also comes back with that episode, paused where it was left (asked by the user 2026-11-09), unless it was played to the end. The player opens its audio only when it is played, not at launch, so a launch spends no data on a stream that may not be resumed and an offline launch shows no playback error; until then, seeking only moves where it will start.
- **One selection for the sections under the content header** (asked by the user 2026-11-08: Queue, Favorites and Downloaded have selection mode, as New has). - **Clear in Queue and Downloaded** (asked by the user 2026-11-08), at the start of the header like Shows' and New's Refresh, as `user-trash-symbolic` (changed from `edit-clear-all-symbolic` at the user's request, 2026-11-09) with its tooltip and label (Clear Queue, Delete All Downloads), and unavailable when there is nothing to clear. - **Preloading the next episode** (asked by the user 2026-11-08). `GstPlay` holds one stream, so the player keeps two: the one playing, and one that opens the next episode (the queue's first, else the list's next) paused, which buffers its start. Playing that episode swaps them, so it starts at once from where it was left, and the length the waiting one learned is reported then; only the playing one's events are reported at all, and a preload that fails is only not preloaded. It starts once the playing episode has first finished buffering, so the two never compete for the connection, follows "up next" as the queue changes, and is skipped on a metered connection (`GNetworkMonitor`, through the network portal in the sandbox, no new permission), where it would spend data on an episode that may never play. A downloaded episode preloads from its file.
